S7 Labs — Home Lab

Running

A physical home server running my personal services in Docker, exposed safely to the internet through Cloudflare Tunnel — no inbound ports opened.

Read the engineering story

Problem

I wanted to self-host real applications (this portfolio, a photo library, side projects) on my own hardware without exposing my home network.

Solution

An Ubuntu box running everything in Docker, published via Cloudflare Tunnel so ingress is zero-trust — the origin never listens on a public port.

Networking

Cloudflare edge terminates TLS and handles DNS for s7labs.dev; the tunnel maps hostnames to local container ports over HTTP internally.

Security hardening

SSH bound to localhost only (systemd socket activation), tunnel-only exposure, and per-service scoping — reducing the public surface to just the tunnel.

Interesting challenges

Correct tunnel origin scheme (HTTP vs HTTPS), socket-activated SSH quirks, and keeping services isolated.

Result

Multiple services running reliably behind one domain — this page is served from it.

03 Case Studies

Not "here's what I built" — "here's a hard problem and how I approached it." Details are generalized to avoid anything proprietary.

Reducing BigQuery query cost & runtime

−25% slots

Problem

Core analytical queries were scanning far more data than needed and consuming excessive slots, driving up both runtime and cost.

Investigation

Profiled query plans and job stats to find the hotspots — full-table scans, wide reads, and redundant transformations repeated across dependent queries.

Approach

Introduced partitioning & clustering on high-selectivity keys, pruned unnecessary columns, restructured queries to push filters down early, and removed duplicated transformation stages.

Result

~25% reduction in slot consumption and runtime on the targeted workloads, with faster downstream reporting.

What I learned

Partitioning helps only when queries actually filter on the partition key — schema and query design have to be co-designed. Next time I'd bake cost/scan checks into CI earlier.

Latest-per-key dedup without blowing the memory limit

Query that finally ran

Problem

A large dedup kept failing with "resources exceeded" — analytic window sorts buffered entire partitions per worker.

Investigation

Traced it to QUALIFY ROW_NUMBER() OVER (PARTITION BY key ORDER BY ts) patterns; the limit is per-worker, so splitting into temp tables didn't help a single oversized partition.

Approach

Rewrote the latest-per-key dedup as a top-1 heap using ARRAY_AGG(STRUCT(...) ORDER BY ts DESC LIMIT 1)[OFFSET(0)] — keeping one row per key in memory instead of the whole partition. Only the large-table dedups were converted; tiny dimension tables stayed simple.

Result

The query completed reliably; the memory ceiling was no longer the bottleneck.

What I learned

Window functions are convenient but hide huge memory costs on skewed/large partitions. Aggregation-based rewrites are worth the extra verbosity at scale.
